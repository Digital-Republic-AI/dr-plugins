Checked against developers.cloudflare.com on 2026-11-06.

## API token

Create it in the dashboard: My Profile > API Tokens > Create Token (or Account API Tokens for a token owned by the account, which survives a person leaving). Grant only what the chosen steps need:

| Step | Permission |
|------|------------|
| Workers deploy | Template "Edit Cloudflare Workers", restricted to the account and, for Custom Domains, to the zone |
| Pages deploy | Account > Cloudflare Pages > Edit |
| Pages custom domain (`pages-domain`) | Account > Cloudflare Pages > Edit |
| DNS record (`dns`) | Zone > DNS > Edit and Zone > Zone > Read, on the zone |
| Access (`access`) | Account > Access: Apps and Policies > Edit and Account > Access: Organizations, Identity Providers, and Groups > Edit, plus Zone > Zone > Read on the protected zones (to check them) |

The CI token needs only the deploy permission; Access and DNS are one-time setup, so give them to a separate short-lived token used on the developer's machine.

The token goes into the environment (`CLOUDFLARE_API_TOKEN`) or into the CI secret store. Never write it into a file in the repository, a `.env` that is committed, a script, or the chat. When the user needs to export it in this session, suggest they type `! export CLOUDFLARE_API_TOKEN=...` themselves, or keep it in their shell profile or keychain; do not ask them to paste it in a message. `CLOUDFLARE_ACCOUNT_ID` is not a secret (it is shown in the dashboard URL), but keep it with the token for consistency.

`node <skill>/scripts/cf-publish.mjs auth` checks the token without printing it (`/user/tokens/verify`, or `/accounts/{id}/tokens/verify` for account tokens).

## Manual script

`scripts/deploy-cloudflare.sh` (generated by `scaffold`, on by default): checks authentication (`CLOUDFLARE_API_TOKEN` or a previous `wrangler login`), runs the build script through the project's package manager, checks that `<dir>/index.html` exists, and deploys with `npx wrangler@4`. For Pages it takes the branch as the first argument (`./scripts/deploy-cloudflare.sh` publishes production, `./scripts/deploy-cloudflare.sh feature-x` publishes a preview).

`wrangler login` (browser OAuth) is the simplest for a person deploying from their own machine; the token is for CI and for the API steps.

## GitHub Actions

`.github/workflows/deploy-cloudflare.yml` (generated with `--git github-actions`) uses `cloudflare/wrangler-action@v4`:

- Workers: runs on pushes to the production branch and on manual dispatch, and calls `wrangler deploy`.
- Pages: runs on every push. The production branch publishes production; other branches publish previews (`--branch=${{ github.ref_name }}`). It needs `deployments: write` and passes `GITHUB_TOKEN` so the deploy shows up in the GitHub deployments panel.

Repository secrets (Settings > Secrets and variables > Actions): `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. With the GitHub CLI the user can set them without the value going through the chat; `gh secret set` prompts for the value when no `--body` is given:

```bash
gh secret set CLOUDFLARE_API_TOKEN
gh secret set CLOUDFLARE_ACCOUNT_ID
```

Suggest running them with the `!` prefix so the prompt appears in their terminal. Do not run `gh secret set --body <token>` yourself.

When the project builds, the workflow installs with the lockfile's package manager (`npm ci`, `pnpm install --frozen-lockfile`, ...). If there is no lockfile, `npm ci` fails: tell the user to commit one, or change the step to `npm install`.

## Native integration

Cloudflare builds and deploys on every push, with no workflow file. Done in the dashboard; there is no file to generate besides `wrangler.jsonc`. Walk the user through it and confirm each value.

### Workers Builds (Workers)

1. Commit and push `wrangler.jsonc` first.
2. Dashboard > Workers & Pages > Create > Import a repository (or, for an existing Worker, Settings > Builds > Connect), authorize the Cloudflare GitHub or GitLab app on the repository.
3. The Worker name in the dashboard must be the same as `name` in `wrangler.jsonc`, or the build fails.
4. Build command: the project's build (`npm run build`), or empty for a site without build. Deploy command: `npx wrangler deploy`.
5. Production branch: the one the user chose (default `main`). Other branches produce preview builds with a preview URL; with `preview_urls: false` (protected site) those URLs are off.
6. Root directory: the folder with `wrangler.jsonc`, when the site lives in a subfolder of a monorepo.

If the repository has no Wrangler config, Workers Builds can detect the framework and open a PR with one; prefer the scaffolded config so the choices made here (SPA, domains, `workers_dev`) are kept.

### Pages Git integration (Pages)

1. Dashboard > Workers & Pages > Create > Pages > Connect to Git, choose the repository.
2. Production branch, build command (empty when there is none) and build output directory (the `--dir`).
3. Every push to another branch creates a preview deployment.

A Pages project created with Direct Upload (`wrangler pages project create` or a manual deploy) can never be switched to Git integration. If the user wants native Git integration on Pages, the project must be created through "Connect to Git" from the start; do not run `pages project create` in that case. If a Direct Upload project already exists, the alternatives are GitHub Actions on the same project, or a new project under a different name.

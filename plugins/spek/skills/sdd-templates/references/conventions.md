# SDD Conventions

This document describes the on-disk conventions of the spec-driven development (SDD) flow: feature
directory naming, the state file schema, phase-detection mechanics, support for multiple parallel
features, the brownfield flow, and the criteria for choosing between light and normal mode.

## Feature directory naming

Each feature lives in its own directory under `.spek/specs/`, named `.spek/specs/NNN-slug/`, where `NNN` is a
zero-padded, sequential 3-digit number (e.g. `001`, `002`, `010`) and `slug` is a short, kebab-case
description of the feature (e.g. `login-google`, `checkout-pix`).

### Artifact layout

```text
<user-project-root>/
└── .spek/
    ├── constitution.md          # single, global to the project (phase 0)
    └── specs/
        ├── 001-login-google/
        │   ├── spec.md
        │   ├── research.md          # optional
        │   ├── plan.md
        │   ├── tasks.md
        │   ├── verify-report.md     # generated by /spek:verify
        │   └── state.json
        ├── 002-checkout-pix/
        │   ├── baseline.md          # brownfield only: written by /spek:extract
        │   └── ...
        └── 003-header-copy-fix/     # example of a feature in "light" mode
            ├── spec.md
            └── state.json
```

Per feature, the artifacts are: `baseline.md` (brownfield features only), `spec.md`, `research.md`
(optional), `plan.md`, `tasks.md`, `verify-report.md`, and `state.json`. The project
constitution, `.spek/constitution.md`, is a single global file outside `.spek/specs/`, produced in phase 0.

All artifacts live in the user's own repository -- never inside the plugin -- and are versioned in
git alongside the code. This is what allows specs to be reviewed in a pull request like any other
engineering artifact.

## The `state.json` schema

Each feature directory carries a `state.json` file that tracks its current state:

```json
{
  "feature": "001-login-google",
  "slug": "login-google",
  "mode": "normal",
  "context": "greenfield",
  "phase": "tasks",
  "created": "2026-08-30T14:00:00Z",
  "updated": "2026-08-30T15:32:00Z",
  "history": ["specify", "clarify", "plan", "tasks"],
  "totalTasks": 14,
  "completedTasks": 0,
  "branch": "001-login-google"
}
```

Field reference:

- `feature` -- the full directory name (`NNN-slug`).
- `slug` -- the feature slug without the sequence number.
- `mode` -- `light` or `normal` (see below). It is the *effort level* of the change.
- `context` -- `"greenfield"` | `"brownfield"`. Whether the change starts from existing code
  (`brownfield`, set by `/spek:extract` right after `init`) or from nothing (`greenfield`, the
  default written by `init`). It is **independent of `mode`**: a brownfield feature can be `light`
  or `normal`, exactly like a greenfield one. Never use `mode` to express this distinction.
- `phase` -- the current phase; see the allowed values below.
- `created` / `updated` -- ISO 8601 timestamps.
- `history` -- ordered list of phases the feature has passed through.
- `totalTasks` / `completedTasks` -- task counters, populated once `tasks.md` exists.
- `branch` -- the git branch associated with the feature, when applicable.
- `handoff` -- optional. Where the last `/spek:implement` run stopped:
  `{ "status": "in-progress" | "failed", "tasks": ["T004", ...], "note": "...", "at": "<ISO 8601>" }`.
  `in-progress` is written BEFORE a batch is dispatched, so a session terminated mid-batch leaves
  it behind for the next run to find; `failed` replaces it when one or more tasks of the batch
  fail, with the error summary in `note`. `tasks` lists the batch (or the failed tasks) and may be
  empty for a light-mode feature, which has no `tasks.md`. Absent whenever nothing is pending
  from an interrupted run.

Field lifecycle: `/spek:specify` creates the file with `feature`, `slug`, `mode`, `context`, `phase`,
`created`, `updated`, `history`, and `branch` (`null` until the git branch is created). In the
brownfield flow the file is created earlier: `/spek:extract` runs `init ... normal extract` (phase
`extract`, `history: ["extract"]`) followed by `set-context brownfield`, and `/spek:specify` then
advances it with `set-phase specify` instead of calling `init` (which refuses to overwrite an
existing state file). `/spek:tasks` adds `totalTasks` and `completedTasks`. `/spek:implement` writes `handoff`
(`update-state.sh set-handoff`) before each batch and removes it (`clear-handoff`) once the batch
succeeds, or rewrites it as `failed` when a task fails; any `set-phase` to a phase other than
`implement` removes it too, so a regenerated `tasks.md` or a finished implementation never leaves a
stale task reference behind. Every command that advances a phase appends to `history` and
refreshes `updated`. A field absent because its phase has not happened yet is normal, not
corruption.

### Allowed `phase` values

`extract`, `specify`, `clarify`, `plan`, `tasks`, `implement`, `implement-complete`, `verified`,
`archived`. `extract` only ever appears as the first phase of a brownfield feature.

## Phase-detection mechanism

No command relies on conversation memory to know "where the feature stopped." Every phase decision
is derived from two signals, in this priority order:

1. **Direct read of `state.json`** (primary source, fast): each command reads the `phase` field
   before acting. This is what lets a brand-new session -- with no conversation history -- resume
   exactly where work stopped, instead of needing the full requirement, design decisions, and task
   progress re-fed into the model.
2. **Physical presence of artifacts** (verification/fallback source): if `state.json` is missing
   or corrupted (e.g. hand-edited by the user), commands infer the phase from which files exist:
   - `tasks.md` exists with all checkboxes ticked -> `implement-complete`.
   - `tasks.md` exists with pending checkboxes -> `implement` (or `tasks` when no checkbox is
     ticked yet -- either way the next step is `/spek:implement`).
   - only `plan.md` exists -> `tasks` pending.
   - only `spec.md` exists, without `[NEEDS CLARIFICATION]` markers -> `plan` pending.
   - `spec.md` exists with `[NEEDS CLARIFICATION]` markers -> `clarify` pending.
   - only `baseline.md` exists, with no `spec.md` -> `extract` done, `specify` pending (the feature
     is brownfield).

   This inference must rewrite `state.json` to restore it as the primary source of truth.
   `scripts/resolve-next.sh` implements the inference (reporting `"stateSource": "inferred"`) and
   `/spek:next` performs the rewrite through `update-state.sh` (`init` with the inferred phase,
   then `set-context brownfield` when `baseline.md` exists and `sync-tasks` when `tasks.md`
   exists).

The `PreToolUse` hook uses exclusively the second mechanism (file presence), since it is cheaper to
check in bash without full JSON parsing -- validating the complete state file is the responsibility
of the commands, not the hook.

## Multiple parallel features

The state model is entirely per-directory (`.spek/specs/NNN-slug/state.json`), so multiple parallel
features never compete for any shared file besides the sequential number `NNN` -- whose resolution,
in `/spek:specify`, always reads the current state of `.spek/specs/` at creation time, preventing number
collisions even with specs created in concurrent sessions.

Practical implications:

- `/spek:status` is the only command with an aggregated view of all features -- it scans
  `.spek/specs/*/state.json` and presents a consolidated dashboard.
- Every other command operates on one feature at a time, resolved either by an explicit slug passed
  as an argument, or, in its absence, by the feature with the most recent `updated` timestamp among
  those that are not yet `verified` or `archived`.
- Two features can be in different phases simultaneously with no cross-blocking -- the phase
  prerequisite hook is scoped to `FEATURE_DIR`, never global to the project.
- Orchestrating parallel implementation work across different features (not just across `[P]` tasks
  within the same feature) is the user's responsibility (e.g. running `/spek:implement` for each
  feature in separate git worktrees) -- the plugin does not enforce serialization between distinct
  features.

## Navigation

Two commands move through the flow without the user having to know which phase command comes next:
`/spek:start` (entry point: constitution, then `specify` or `extract`, or hand-off to `next` when a
feature is already in progress) and `/spek:next` (advances the current feature by exactly one
step). `/spek:status` reports the same answer without acting on it. All three consume the JSON of
`scripts/resolve-next.sh`, which is the single implementation of the rules below -- commands never
recompute them in prose.

### Current feature

1. An explicit argument wins: `NNN-slug`, the bare `slug`, or the path of the feature directory.
2. Otherwise, the feature with the most recent `updated` timestamp among those whose `phase` is not
   `verified` or `archived`. A feature directory without a valid `state.json` takes part with its
   inferred phase and the directory's modification time.
3. No feature at all, or every feature terminal -> there is no current feature; the next command is
   `start`.

A directory under `.spek/specs/` that holds neither `state.json` nor any artifact is ignored -- it
is a leftover, not a feature.

### Phase -> next command

| `phase` | `mode: normal` | `mode: light` |
|---|---|---|
| `extract` | `specify` (args `--slug=<slug>`, so the spec lands in the same directory) | same |
| `specify`, `clarify` | `clarify` if `spec.md` has `[NEEDS CLARIFICATION]` markers, else `plan` | `clarify` if markers, else `implement` |
| `plan` | `tasks` | n/a (never reached) |
| `tasks` | `implement` | n/a (never reached) |
| `implement` | `implement` while `tasks.md` has pending checkboxes, else `verify` | same |
| `implement-complete` | `verify` | same |
| `verified`, `archived` | `none` (only reachable through an explicit argument) | same |

The marker count and the task counters are always read from `spec.md` and `tasks.md` at resolution
time (same checkbox patterns as `update-state.sh sync-tasks`), never from `state.json`, so the
answer cannot drift from the artifacts.

When the phase is `implement` with pending tasks and `state.json` carries a `handoff`, the reason
also names what to resume, e.g. `tasks.md still has 3 pending task(s); resume at T004 (failed:
test X failed)`. The note is truncated to one line there; the full record is in the `handoff`
field of the feature object.

### Script contract

`resolve-next.sh [feature]` prints one JSON line:

```json
{
  "project": { "spekDir": true, "constitution": false, "featureCount": 2, "activeCount": 1 },
  "feature": {
    "feature": "002-payment-gateway", "slug": "payment-gateway", "dir": "/abs/.spek/specs/002-payment-gateway",
    "phase": "specify", "mode": "normal", "context": "brownfield", "updated": "2026-09-07T12:00:00Z",
    "stateSource": "state",
    "clarifications": 2, "totalTasks": 0, "completedTasks": 0, "pendingTasks": 0,
    "handoff": null,
    "artifacts": { "baseline": true, "spec": true, "plan": false, "tasks": false, "verifyReport": false }
  },
  "next": { "command": "clarify", "args": "002-payment-gateway", "reason": "spec.md has 2 [NEEDS CLARIFICATION] marker(s)" }
}
```

`feature` is `null` when there is no current feature. `next.command` is one of `start`, `specify`,
`clarify`, `plan`, `tasks`, `implement`, `verify`, `none`; `next.args` is what the navigation
command passes to the target command. `stateSource` is `state` or `inferred` (see "Phase-detection
mechanism"). `handoff` is the `state.json` field of the same name copied verbatim, or `null` when
absent or when the state was inferred; `start`, `next` and `status` display it, `implement` acts
on it. The script never writes anything.

### Invocation between commands

A navigation command runs the target command through the `Skill` tool (`skill: "spek:<command>"`),
listing every possible target as `Skill(spek:<command>)` in its `allowed-tools`. A target must not
carry `disable-model-invocation: true`, which is why `constitution.md` does not (it is still only
run on explicit user request, directly or through `/spek:start`), while `quick.md` keeps it (no
navigation command routes to it). `start` invokes `next` only when an active feature exists and
`next` invokes `start` only when none does, so the two never loop; neither chains more than one
phase command per run.

## Language

Every artifact is written in English, whatever language the user writes in: constitution,
baseline, spec, research, plan, tasks, verify report, and the notes stored in `state.json`. The
conversation with the user (questions, notices, summaries) follows the user's language. Two
details: text the user supplied that a template records verbatim as input (the spec's
"Original user description") is kept as given; everything the plugin phrases itself, including a
clarification decision that lands in the spec, is written in English. Identifiers (`FR-00X`,
`SC-00X`, `PR-00X`, `BR-00X`, `T00X`), section headings and status labels stay literal, since
commands and agents match on them.

## Brownfield flow

A feature whose change starts from code that already exists enters the flow one step earlier, and is
marked `"context": "brownfield"` in its state file:

```text
/spek:extract <path>
  -> baseline.md: what the code does TODAY, with BR-00X responsibilities and [CANNOT INFER] gaps
  -> state.json: phase="extract", context="brownfield", mode="normal"
/spek:specify "<the change you actually want>"
  -> spec.md with the three Scope Boundaries zones (What Changes / What Must Be Preserved /
     Out of Scope), promoting the relevant BR-00X baseline entries into PR-00X preservation
     requirements
  -> set-phase specify (the state already exists; init is not called again)
-> clarify (if needed) -> plan -> tasks -> implement -> verify, exactly as in the greenfield flow
```

**Baseline immutability**: once `spec.md` exists in the feature directory, `baseline.md` is frozen.
It is the approved historical record of how the system was before the change, and rewriting it would
destroy the ability to verify regressions against it. This is enforced by the phase-prerequisite hook
(`hooks/scripts/check-phase-prereq.sh`), which blocks `Write`/`Edit` on `baseline.md` whenever
`spec.md` is present in the same feature directory. If a fresh baseline is needed, run
`/spek:extract` for a new feature instead of editing the old one.

**Verification**: on a brownfield feature `/spek:verify` checks two things, not one -- the change
spec (each `FR-00X` / Success Criterion of `spec.md`) *and* the preservation zone (each `PR-00X`
under `### What Must Be Preserved`), each with concrete evidence. A change that ships its new
behaviour while silently breaking a preserved one is a failed verification, not a partial success.

## Light vs normal mode

### Detection criteria (applied in `/spek:specify`)

| Signal | `light` mode | `normal` mode |
|--------|--------------|----------------|
| Estimated affected files | <= 3 | > 3 |
| Estimated lines of code | < 10 (or purely cosmetic/copy) | >= 10, or introduces a new component/API |
| Number of identifiable user stories | 0 or 1 trivial | >= 1 non-trivial, or >= 2 |
| Introduces a new external dependency | No | Possibly |
| Affects an API contract or data schema | No | Possibly |

The estimate of affected files/lines is produced by the `/spek:specify` command itself (the main
agent, never a subagent) based on the user's description and, when useful, a light scan of related
code (`Grep`/`Glob`) -- it is a heuristic, not a guarantee. The `spec-writer` subagent receives the
mode already resolved and writes `spec.md` directly in that format, reporting only completion back
to the command. The estimate is only a SUGGESTION, and `normal` is the default: a `normal`
estimate proceeds without interrupting the user, while a `light` suggestion -- the only one that
removes safeguards, by skipping plan and tasks -- must be confirmed via `AskUserQuestion` before
being written to the state. When signals conflict or the description is too thin to estimate, the
suggestion must be `normal`. An explicit `--mode=` override skips estimation and confirmation
entirely -- it is itself a user decision.

### Flow differences between modes

**Light mode**:

```text
/spek:specify "fix checkout button text"
  -> generates a condensed spec.md (no formal User Stories, just a description and minimal FRs)
  -> state.json: mode="light", phase="specify"
  -> skips /spek:plan and /spek:tasks
  -> suggests going straight to /spek:implement, which works from the condensed spec.md
  -> /spek:verify still always runs at the end (verification is never skipped)
```

**Normal mode**:

```text
/spek:specify "add checkout with Pix"
  -> full spec.md (prioritized User Stories, numbered FRs, measurable Success Criteria)
  -> state.json: mode="normal", phase="specify"
  -> full flow: clarify (if needed) -> plan -> tasks -> implement -> verify
```

### Light-mode spec format

Light mode still produces a real `.spek/specs/NNN-slug/spec.md` -- it is a condensed spec, not the absence
of one. Its format is fixed:

**Title header block** -- identical to the full template:

```markdown
# Feature Specification: [FEATURE NAME]

**Feature Branch**: `[NNN-feature-slug]`
**Created**: [DATE]
**Status**: Draft
**Input**: Original user description: "$ARGUMENTS"
```

**`## Change Description`** -- 2 to 6 sentences stating what changes and why. Plain prose, no user
stories, no journey narrative.

**`## Functional Requirements`** -- numbered `FR-00X` entries, typically 1 to 4. Each one must be
objectively verifiable, exactly as in normal mode. `[NEEDS CLARIFICATION: specific question]` markers
are allowed and follow the same rule: mark the ambiguity instead of assuming a default.

**`## Acceptance Check`** -- 1 to 3 plain checkable statements describing how a reviewer confirms the
change is done (e.g. "the checkout button reads 'Finish order' in pt-BR and en-US"). No metrics, no
Given/When/Then ceremony.

**`## Clarifications`** -- same contract as the full template: filled in incrementally by
`/spek:clarify`, never edited by hand.

The canonical skeleton is `references/spec-light-template.md`, scaffolded by the `sdd-templates`
skill (`scaffold.sh spec-light <feature-dir>`); `references/spec-template.md` is the normal-mode
counterpart (`scaffold.sh spec <feature-dir>`).

**Explicitly absent sections**: User Stories, Success Criteria metrics (SC-00X), Key Entities, and
Edge Cases. These are deliberately not part of the light format. If while writing the spec the author
feels the need for any of them, that is a signal the change is not trivial and should be `normal`
mode -- promote the feature instead of bending the light format.

**Downstream contract**: `/spek:implement` in light mode works from the Functional Requirements plus
the Acceptance Check of this condensed spec (there is no `plan.md` or `tasks.md` to consume).
`/spek:verify` checks each FR and each Acceptance Check item with evidence, exactly as it does in
normal mode -- verification is never relaxed because the mode is light.

### Manual override

Every command accepts an explicit mode override from the user (e.g.
`/spek:specify --mode=normal "copy adjustment"` for a small but sensitive change, such as
compliance/legal text, where formal review is desired even though it is technically trivial). The
`mode` field in `state.json` always reflects the final decision (automatic or forced), and the
other commands (`plan`, `tasks`) must check this field and refuse to run on a `light` feature unless
the user explicitly asks to "promote" the feature to normal mode (in which case the command simply
updates `mode` and proceeds normally from the existing `spec.md`).

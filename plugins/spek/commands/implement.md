---
description: Executes a feature's pending tasks, one by one or in parallel batches, updating progress
argument-hint: "[NNN-slug of the feature] [--task ID | --story US1 | --all]"
allowed-tools: Read, Write, Edit, MultiEdit, Bash, Glob, Grep, Task

# Implement

## Steps

1. Resolve the target feature from `$ARGUMENTS` and verify that `.spek/specs/NNN-slug/tasks.md` exists. If
   the feature's mode is `"light"` (see `state.json`), tasks.md may not exist -- in that case,
   work directly from the summary generated by `/spek:specify` without requiring the full artifact.

2. Read `tasks.md` and identify tasks with checkbox `[ ]` (pending) vs `[x]` (done).

   If `state.json` has a `handoff` field, report it in one line before executing anything: its
   `status`, `tasks` and `note`. When the status is `in-progress`, the previous session was
   terminated in the middle of those tasks -- warn the user that their files may hold partial
   edits. When it is `failed`, the note carries the error summary of the last run. Either way the
   tasks are still `[ ]` in `tasks.md`, so they enter the scope below normally: a handoff is a
   resumption, never a reason to stop.

3. Determine the execution scope from the arguments:
   - No scope argument: runs the ENTIRE next pending phase (every pending task of that phase),
     then stops and reports. Run the command again to advance to the following phase.
   - `--all`: runs ALL pending phases sequentially, phase by phase, in a single invocation, and
     only stops early at the first failed task (see step 7). It is not one phase per invocation.
   - `--task ID`: runs only the specified task.
   - `--story US1`: runs all pending tasks of that user story, respecting dependencies.

4. Before executing the first task of this run, mark the feature as under implementation by running
   `${CLAUDE_PLUGIN_ROOT}/scripts/update-state.sh .spek/specs/NNN-slug set-phase implement`.
   Then, for tasks marked `[P]` within the scope (same phase, no dependency between them), delegate
   parallel execution to the `spek:implementer` subagent via multiple concurrent invocations of the
   `Task` tool. For tasks without `[P]`, execute them sequentially in the listed order. Each
   invocation receives the task line verbatim (ID, story, description, file path) and the PATHS of
   `.spek/specs/NNN-slug/spec.md`, `.spek/specs/NNN-slug/plan.md` and, if it exists,
   `.spek/constitution.md` -- the subagent reads the sections it needs; never paste artifact
   content into the prompt.

   Immediately BEFORE dispatching each batch (one sequential task, or the group of `[P]` tasks of
   the phase), record it by running
   `${CLAUDE_PLUGIN_ROOT}/scripts/update-state.sh .spek/specs/NNN-slug set-handoff in-progress "<short batch description>" <ID ...>`
   with the IDs of the batch (for a light-mode feature without `tasks.md`, pass no IDs and describe
   the spec section being worked on). Writing it before, not after, is what lets a session killed
   mid-batch be resumed by the next run. When a batch resumes tasks named in an `in-progress`
   handoff (step 2), add one instruction to each of those `spek:implementer` invocations: inspect
   the current state of the task's files before editing, because an earlier run may have been
   interrupted halfway through them.

5. After each task completed successfully:
   - Tick the corresponding checkbox in `tasks.md` (`[ ]` -> `[x]`).
   - Run `${CLAUDE_PLUGIN_ROOT}/scripts/update-state.sh .spek/specs/NNN-slug sync-tasks`, which re-counts
     the checkboxes in `tasks.md` and rewrites `totalTasks`/`completedTasks` from them, refreshing
     `updated`. The counters are always DERIVED from `tasks.md` (the source of truth), never
     incremented, so they can never drift. Never hand-edit `state.json`.
   - Once every task of the batch has completed successfully and `sync-tasks` has run, clear the
     record with `${CLAUDE_PLUGIN_ROOT}/scripts/update-state.sh .spek/specs/NNN-slug clear-handoff`.
   - If all tasks of a phase are done, report it in the console for the user.

6. If all tasks in `tasks.md` are done, run
   `${CLAUDE_PLUGIN_ROOT}/scripts/update-state.sh .spek/specs/NNN-slug set-phase implement-complete`
   and suggest `/spek:verify` as the next step.

7. If a task fails (execution error, breaking test), stop the execution of that batch, do NOT tick
   the checkbox, and report the error clearly to the user. Tick the tasks of the batch that did
   succeed, run `sync-tasks`, then record the failure with
   `${CLAUDE_PLUGIN_ROOT}/scripts/update-state.sh .spek/specs/NNN-slug set-handoff failed "<error summary per failed task>" <failed ID ...>`
   so the next run (and `/spek:next`, `/spek:start`, `/spek:status`) knows where and why it
   stopped. Under `--all`, the first failed task stops the whole run -- do not move on to the
   remaining phases.

## Rules

- Never mark a task as complete without first confirming that the expected file/change actually
  exists (re-read the file after the edit).
- Tasks from different phases never run in parallel with each other, only `[P]` tasks within the
  same phase and with no declared dependency.
- If the user asks to implement something outside the scope of `tasks.md`, stop and ask whether the
  plan/tasks should be updated first (never silently "invent" tasks).
- The `handoff` field of `state.json` is written and cleared only through `update-state.sh`
  (`set-handoff`, `clear-handoff`), never by editing the file. Its note is written in English. An `in-progress` handoff found at
  the start of a run is a resumption, never a failure: report it, warn about partial edits, and
  carry on with the normal scope.
